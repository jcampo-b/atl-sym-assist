Added HTTP-level caching (`Cache-Control: private, max-age`), Redis-level caching via `Cache::flexible` and `Cache::remember` on all major endpoints (property-performance, vacancy, tasks, planner/today, planner/upcoming), a version key (`TaskCacheVersion`) to invalidate task caches on mutations, and an artisan dev-benchmarking command (`rm:diff-permissions`).

## Findings

### BLOCKER

**`app/Modules/DailyPlanner/Controllers/DailyPlannerController.php`**
- Severity: blocker
- What: No feature tests for `GET /api/daily-planner/today` or `GET /api/daily-planner/upcoming`. The response shape changed (`{data, meta:{warnings:[]}}`) and is completely untested.
- Why: Rule — every new/modified endpoint needs a feature test.
- Fix: Add feature tests asserting the `{data: [], meta: {warnings: []}}` shape and the `?refresh=1` bypass path.

**`app/Modules/Tasks/Services/TaskCacheVersion.php` — `bump()` (lines ~40–43)**
- Severity: blocker
- What: `Cache::add()` + `Cache::increment()` is non-atomic. Between the two calls a concurrent request can read version `0` after `add` but before `increment`, producing a stale cache key. The docblock says "instantly become orphans" which overstates the atomicity guarantee.
- Why: Non-atomic increment = TOCTOU race on concurrent writes. Failure mode: one extra cache miss per race window (not data corruption).
- Fix: Use `Cache::increment($key)` alone (Redis INCR initializes to 1 on missing key) and handle TTL separately, OR document the race window as accepted and fix the misleading docblock claim.

### SHOULD-FIX

**`app/Modules/Integrations/RentManager/Services/RentManagerService.php` — `poolVacancy()`**
- Severity: should-fix
- What: `poolVacancy` specs don't include a `map` callable — raw RM rows leak into `VacancyService` (SA layer), which then calls RM mapper methods directly. `poolDashboard` correctly applies mappers inside the RM layer.
- Why: Layer discipline — SA layer must not consume raw RM field-named rows. RM mapper calls must stay in the RM layer.
- Fix: Apply the appropriate `RentManagerVacancyMapper` method as a `map` callable in each `poolVacancy` spec (same pattern as `poolDashboard`).

**`app/Modules/Tasks/Services/TaskService.php` — `list()` — `Cache::remember` vs `Cache::flexible`**
- Severity: should-fix
- What: Task list uses `Cache::remember` (hard expiry), while all dashboard/planner endpoints use `Cache::flexible` (SWR). After a `TaskCacheVersion::bump()` a user is guaranteed to wait for a cold fetch instead of getting an instant stale response.
- Why: Inconsistency undermines the performance goal. Hard expiry after bump = the cold-path problem is reintroduced for active users.
- Fix: Consider `Cache::flexible($cacheKey, [300, 900], ...)` to match dashboard behavior. If intentional, add a comment explaining WHY `remember` was chosen over `flexible`.

**RESTClient files — missing `?refresh=1` examples**
- Severity: should-fix
- What: The new `?refresh=1` parameter is not documented as a runnable example in `RESTClient/tasks.http`, `RESTClient/dashboard.http`, or `RESTClient/daily-planner.http` for any of the newly cached endpoints.
- Why: Rule — new/changed endpoints must have a runnable example in the relevant `.http` file.
- Fix: Add `?refresh=1` example requests for all cached endpoints.

**`app/Modules/Tasks/Services/TaskCacheVersion.php` — no unit tests**
- Severity: should-fix
- What: New public service class with three public methods (`key`, `current`, `bump`) — no unit tests.
- Why: Rule — every new public method on a Service needs a unit test.
- Fix: Add `tests/Unit/Modules/Tasks/Services/TaskCacheVersionTest.php` covering: `current()` returns 0 when key absent, `bump()` increments the counter, `bump()` is idempotent on TTL seeding, `key()` includes user id.

### NIT

**`app/Console/Commands/DiffRentManagerPermissions.php` — line 71**
- `crc32($username)` can return a negative integer on 64-bit PHP → cache keys like `tasks_ver_-1234567890`. Use `abs(crc32($username))` or `sprintf('%u', crc32($username))`.

**`app/Modules/Integrations/RentManager/Services/RentManagerHttpClient.php` — `applyGetRetry()` ~line 340**
- The retry closure `function (\Throwable $e): bool` falls off the end if `$e` is neither `ConnectionException` nor `RequestException` — implicit `null` return in a `bool`-typed closure. PHPStan level 5 will catch this. Fix: add `return false;` as the final line.

**`app/Modules/DailyPlanner/Services/DailyPlannerService.php` — `buildToday()` / `buildUpcoming()`**
- Immediately-called closure (`$build = function() {...}; return $build()`) is over-indirection. Inline the logic directly with an `if ($profiling)` branch. Minor style nit.

**`docs/performance-strategy.md`**
- Status line says `proposal — implementation happens in follow-up cards` but Phases 1–3 are fully implemented in this PR. Update to reflect actual shipped state.
