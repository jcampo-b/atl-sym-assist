## Findings

### Blockers

#### 1. Modifying base migration instead of creating a standalone one
- **File + line:** `database/migrations/0001_01_01_000000_create_users_table.php:29-32`
- **Severity:** blocker
- **What's wrong:** The 4 new `linked_*_id` columns were added to the original base migration instead of a new timestamped migration file.
- **Why:** Any environment where the `users` table already exists (staging, production, other dev machines that ran `migrate` before this PR) won't pick up the new columns — the migration has already been recorded as run. The code will throw `SQLSTATE[42S22]: Column not found` when anything tries to use `linked_owner_id` etc.
- **Suggested fix:** Revert the changes from `0001_01_01_000000_create_users_table.php` and create a new migration: `php artisan make:migration add_linked_entity_ids_to_users_table`. Move the 4 column definitions there. The base migration should only be modified for truly brand-new projects with no existing DB — and even then the convention is a standalone migration.
- **Comment for the dev:** "The `0001` migration has already been recorded as run in every existing environment. Adding columns here won't execute on staging/prod — it'll only apply on a fresh install. Please create a new migration (`add_linked_entity_ids_to_users_table`) with these 4 columns. The commit history shows you started with a standalone migration and then consolidated — the original approach was actually correct."
