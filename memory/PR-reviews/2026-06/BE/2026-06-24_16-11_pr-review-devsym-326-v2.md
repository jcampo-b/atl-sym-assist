## Findings

### Blockers

**1. `app/Modules/Users/Services/RoleService.php:27` — PascalCase `RoleID` in SA layer**
`isset($raw['RoleID'])` reads an RM PascalCase field directly from an SA service.
Violates cardinal layer rule (AGENTS.md). Fix: add `RentManagerRoleMapper::extractRoleId()`
mirroring `RentManagerUserMapper::extractUserId()` and use it.

**2. `app/Modules/Integrations/RentManager/Services/RentManagerUserService.php:80-96` —
`enableApiAccess` silently produces a broken payload when `getUser` returns empty**
If RM returns 404 or empty body after creation, `$current = []`, `sanitizePayload` drops all
nullable fields, and RM rejects the partial POST with 500. User created but can't log in, no
error surfaced. Fix: guard `if (empty($current['Username'])) throw new \RuntimeException(...)`.

### Should-fix

**3. `app/Modules/Users/Services/UserService.php:163` — `create()` returns stale `has_api_access`**
`$raw` from `Users/AddUser` never contains `HasAPIAccess`. Final response always shows
`has_api_access: null` even after activation. Fix: after enableUserApiAccess call, set
`$raw['HasAPIAccess'] = true` before the final return.

**4. `tests/Unit/Modules/Users/Services/UserServiceCreateTest.php` — no test for `has_api_access=false`**
`stubCreate()` unconditionally expects `enableUserApiAccess` once; the `false` branch is never
exercised. Fix: add one test with `shouldNotReceive('enableUserApiAccess')`.

**5. `app/Modules/Integrations/RentManager/Services/RentManagerUserService.php:44` — stale TODO**
"TODO: orquestar los 3 pasos" — orchestration now lives in `UserService::create` (SA layer,
correct place). Comment is outdated and misleading. Remove or update.

### Nits

**6. `config/rent_manager.php:71` — hardcoded tenant-specific default role IDs (808/809/810)**
Code handles missing config correctly (returns null). Just needs a comment that these
defaults are tenant-specific, not universal.

**7. `RESTClient/users-creation.http` — `@saUserId` vs `createUserSAFull` ambiguity**
Verify call near the user_type example reads `{{saUserId}}` from a different create call.
The new `@name createUserSAFull` has its own verify, so functionally fine, but could
confuse sequential runs.
