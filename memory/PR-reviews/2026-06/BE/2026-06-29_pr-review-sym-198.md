### Should-Fix

#### 3. `Auth::user()` passed directly to `User`-typed parameter
- **File + line:** `app/Modules/Onboarding/Controllers/OnboardingMeController.php:18`
- **Severity:** should-fix
- **What's wrong:** `Auth::user()` (type `Authenticatable|null`) passed directly to `resolveMe(User $user)` (non-nullable `User`). Larastan level 5 will flag this.
- **Why:** Existing codebase pattern (`RentManagerHttpClient.php:53, 107`) always assigns to variable + null-checks first. This breaks that pattern.
- **Suggested fix:** `/** @var \App\Models\User $user */ $user = Auth::user();` then pass `$user`.
- **Comment for the dev:** "`Auth::user()` returns `Authenticatable|null` — Larastan level 5 will flag passing it directly to a `User $user` param. The existing codebase (see `RentManagerHttpClient`) always assigns to a variable first. Please add a `@var` annotation: `/** @var User $user */ $user = Auth::user();`."

#### 4. `RentManagerOwnerMapper::detectMissing()` called from Tenant and Vendor step classes
- **File + line:** `app/Modules/Onboarding/Steps/TenantOnboardingSteps.php:57`, `app/Modules/Onboarding/Steps/VendorOnboardingSteps.php:31`
- **Severity:** should-fix
- **What's wrong:** Both classes call `RentManagerOwnerMapper::detectMissing()` — a generic utility that lives on the wrong mapper. The `rmTag()` methods correctly use their own mappers, making the inconsistency visible.
- **Suggested fix:** Extract `detectMissing` to a neutral shared helper or add it to each mapper.
- **Comment for the dev:** "`TenantOnboardingSteps` and `VendorOnboardingSteps` both call `RentManagerOwnerMapper::detectMissing()`. Note that `rmTag()` in both correctly uses the right mapper. Please extract `detectMissing` to a neutral location — the Tenant/Vendor step classes shouldn't depend on the Owner mapper."

#### 5. Hardcoded `pageSize: 1000` with no comment or pagination — silent truncation
- **File + line:** `app/Modules/Onboarding/Services/OnboardingService.php:403, 425, 447`
- **Severity:** should-fix
- **What's wrong:** All three `list*` methods cap at 1000 results with no pagination and no explanation.
- **Suggested fix:** Add comment with follow-up ticket, or accept `$perPage`/`$page` params from the controller.
- **Comment for the dev:** "A cap of 1000 with no pagination and no comment will silently truncate results once the tenant count grows. If this is a known MVP limit, add a comment with a follow-up ticket number. Otherwise, at minimum expose the limit so the FE can tell users the list is capped."

#### 6. `sa_vendor_emp` lookup ignores `linked_vendor_emp_id`
- **File + line:** `app/Modules/Onboarding/Services/OnboardingService.php:476`, `566–568`
- **Severity:** should-fix
- **What's wrong:** `resolveMe` routes `sa_vendor_emp` to `lookupVendorForUser()` which only checks `linked_vendor_id`, never `linked_vendor_emp_id`. Vendor employees with the emp ID set but vendor ID unset fall through to email lookup.
- **Suggested fix:** Add a comment explaining the intentional behavior, or add an early-return branch for `linked_vendor_emp_id`.
- **Comment for the dev:** "`sa_vendor_emp` resolves via `lookupVendorForUser()` which only checks `linked_vendor_id` — `linked_vendor_emp_id` is never consulted. If vendor employees are intentionally looked up as their parent vendor entity, document it with a one-line comment. Otherwise, add a lookup branch for `linked_vendor_emp_id`."
