## Dev's stated focus
Ticket being refactored by Jona — analyze from that angle. Scope: refactor of user / role /
privilege creation and property groups over the RentManager integration. Adds:
`/users/roles` (POST), `/users/privileges` (GET), `/property-groups` (GET/POST), a static
privilege catalog, privilege/property-group RM services + mappers, and `user_type` /
`has_api_access` on user create.

## Findings

### Blockers
1. **`app/Modules/Users/Services/RoleService.php:28` — PascalCase RM field in SA layer.**
   `$raw['RoleID']` is read directly in an SA service. Violates the cardinal layer rule
   (PascalCase RM field names only inside `app/Modules/Integrations/RentManager/`). The
   correct pattern already exists next door: `UserService::create` uses
   `RentManagerUserMapper::extractUserId($raw)`. Fix: add
   `RentManagerRoleMapper::extractRoleId()` and use it.

### Should-fix
2. **Dead live-fetch privilege path.** `RentManagerPrivilegeMapper` (toPrivilege/listParams/
   isVisible), `RentManagerPrivilegeService::getPrivileges`, and `RentManagerService::getPrivileges`
   have no callers — the `/users/privileges` endpoint resolves through the static
   `RentManagerPrivileges::grouped()` catalog. Plus the singleton registration in
   `IntegrationsServiceProvider`. Violates AGENTS "no files/methods with no callers" +
   "no speculative abstractions." Remove, or move to a console/dev tool if it's for
   regenerating the catalog.
3. **Duplicated privilege-payload assembly + enum resolution** in `UserService::create` and
   `RoleService::create` (identical `enumStringFor` + build `{id,enum_string,is_on..is_delete}`
   loop). Push enum resolution into the RM layer (`assignUserPrivilege`/`attachPrivilege`
   resolve `enum_string` from id) so SA passes only `{id, flags}` — removes duplication and the
   SA→catalog coupling.
4. **`StoreUserRequest::withValidator` mutual-exclusion ignores `user_type`.** Guard blocks
   `role_ids` + `custom_privileges` to avoid double-grant, but `user_type` also appends a role
   in `UserService::create` and isn't in the check, so `user_type` + `custom_privileges` still
   double-grants. Confirm intended; if not, fold `user_type` into the guard or document why
   it's exempt.

### Nits
5. `RoleService::create:51` returns `toRole($raw)` from the create-shell — seeded privileges
   not reflected in the response (fine if FE refetches; worth a note).
6. `RentManagerPrivileges::grouped()` sets `label` and `description` to the same value —
   redundant unless the FE contract needs both.
7. `RentManagerUserService::enableApiAccess` defaults `'IsActive' => $current['IsActive'] ?? true`
   — re-post could reactivate a disabled user if `IsActive` were missing. Narrow edge case.

**Strengths:** good unit coverage of new service paths (unknown-id skip, user_type role
resolution, address primary/fallback, property-group mapping); RM quirks documented at call
sites (AddUser can't carry HasAPIAccess, location re-assign 500, nested-privileges-dropped on
Role create); PascalCase otherwise contained to the RM layer.

## Verdict
**Needs changes before merge** — 1 blocker, 3 should-fix, 3 nits.
