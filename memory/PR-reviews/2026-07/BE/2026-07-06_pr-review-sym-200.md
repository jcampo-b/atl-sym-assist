## Dev's stated focus
Adds a single endpoint (`POST /api/onboarding/invite`) so a super-admin can onboard an owner in one request: creates the blank RM Owner entity, optionally a PropertyGroup from `property_ids`, creates the RM user (reusing `UserService::create`), and auto-links the local user to the owner via `linked_owner_id`. Replaces the old manual 2-step (create user → link entity) flow. Owner-only for now; tenant/vendor plug in later via their `*OnboardingDefinition`. Not transactional (documented, accepted risk).

## Findings

### Blocker

**File:** `app/Modules/Onboarding/Services/OnboardingInviteService.php`
```php
    private function resolvePropertyGroup(InviteData $data): ?array
    {
        if (empty($data->property_ids)) {
            return null;
        }

        $group = $this->rentManagerService->createPropertyGroup(
            $data->username.' - properties',
            $data->property_ids,
        )['data'] ?? [];

        $groupId = (int) ($group['PropertyGroupID'] ?? $group['value'] ?? 0);

        return $groupId > 0 ? [$groupId] : null;
    }
```
- **What's wrong:** Raw RM PascalCase field name (`PropertyGroupID`) read directly in the SA layer (`app/Modules/Onboarding/`), outside `app/Modules/Integrations/RentManager/`.
- **Why:** Violates the cardinal layer rule in `AGENTS.md`. Same PR does this correctly for the Owner id via `RentManagerOwnerMapper::extractOwnerId()`, but not for the PropertyGroup id.
- **Suggested fix:** Add an `extractPropertyGroupId()` helper on the RM property-group layer, mirroring `extractOwnerId()`, and call it from the service instead of indexing the raw array.
- **Comment for the dev:** Nice touch adding `extractOwnerId()` to keep `OwnerID` out of the SA layer — can you do the same for `PropertyGroupID` in `resolvePropertyGroup()`? Right now it reads the raw RM field directly, which breaks the layer rule this PR otherwise follows correctly.

### Should-fix

**File:** `app/Modules/Users/Services/UserService.php` (also `LinkUserRequest.php`, `OnboardingService.php`)
```php
        $column = match ($entityType) {
            'sa_owner' => 'linked_owner_id',
            'sa_tenant' => 'linked_tenant_id',
            'sa_vendor' => 'linked_vendor_id',
            'sa_vendor_emp' => 'linked_vendor_emp_id',
            default => throw new \InvalidArgumentException("Unsupported entity_type: {$entityType}"),

```
- **What's wrong:** Renames the accepted `entity_type` values on the existing `POST /api/users/{id}/link` endpoint from `owner|tenant|vendor` to `sa_owner|sa_tenant|sa_vendor|sa_vendor_emp`, and changes the `type` field returned by `GET /api/onboarding/me` the same way — neither is flagged as a breaking change in the PR description.
- **Why:** Code-review skill checklist: breaking API contract changes must be explicitly flagged. Any existing caller sending the old bare values breaks silently.
- **Suggested fix:** Add an explicit breaking-change note to the PR description naming both endpoints and old→new values, or confirm with FE that no consumer depends on the old values yet.
- **Comment for the dev:** This quietly changes the contract of two existing endpoints (`/users/{id}/link` and `/onboarding/me`'s `type` field) from bare `owner/tenant/vendor` to `sa_`-prefixed values. Looks intentional and consistent, but it's not called out as a breaking change in the description — worth flagging explicitly so FE knows to update.
