## Findings

### 🔴 Blockers

**File:** `app/Modules/Onboarding/Services/OnboardingService.php`
```php
public function updateVendor(VendorData $changes): array
{
    // Self-onboarding: read/write the user's OWN entity via the global token
    // (the user's RRM-scoped token can't see its own entity — location scoping).
    return $this->rentManagerService->asSystem(function () use ($changes) {
        $current = $this->rentManagerService->getVendor(
            (string) $changes->vendor_id,
            ['embeds' => 'Contacts,Addresses,Properties'],
        )['data'] ?? [];
```
- **What's wrong:** `updateVendor` (and `updateOwner` L75-79, `updateTenant` L291-295) run the entire
  write under `asSystem()` (global 4MK admin token) with no check that `$changes->vendor_id` belongs
  to the authenticated caller. `vendor_id` comes from the route path; `PATCH /api/onboarding/vendors/{vendorId}`
  (`routes.php:61`) has only `auth:sanctum + rm_token.valid + throttle` (NO `rm_super_admin`); and
  `OnboardingUpdateVendorRequest::authorize()` returns `true`.
- **Why:** Broken access control / IDOR. Previously the caller's RRM-scoped token was the natural
  containment (the code comment itself says a scoped token can't even see its own entity — location
  scoping). `asSystem()` removes it: any authenticated sa_vendor/sa_owner/sa_tenant user can
  `PATCH /onboarding/vendors/{ANY_ID}` and read+overwrite any entity in RM via the admin token.
  Privilege-escalation regression introduced by this diff.
- **Suggested fix:** Assert path id == caller's linked id (`linked_vendor_id`/`linked_owner_id`/
  `linked_tenant_id`), else 403, before entering `asSystem()`. Home: each `OnboardingUpdate*Request::authorize()`
  or a guard clause at the top of each `update*` service method. Exempt super-admin explicitly if needed.
