## Findings

### BLOCKERS

**File:** `app/Modules/Onboarding/Services/OnboardingService.php`
**Code snippet** (`updateTenant`, lines ~332-343):
```php
                if (($row['relationship'] ?? null) !== null) {
                    $this->rentManagerService->saveContactUserDefinedValue($contactId, [
                        'UserDefinedFieldID' => (int) config('rent_manager.tenant_relationship_udf_id'),
                        'Value' => $row['relationship'],
                    ]);
                }
                if (($row['phone'] ?? null) !== null) {
                    $this->rentManagerService->saveContactPhoneNumber($contactId, [
                        'PhoneNumber' => $row['phone'],
                        'PhoneNumberTypeID' => 1,
                        'IsPrimary' => true,
                    ]);
                }
```
**Severity:** blocker
**What's wrong:** RRM PascalCase payloads (`UserDefinedFieldID`, `Value`, `PhoneNumber`, `PhoneNumberTypeID`, `IsPrimary`) are built inline in an SA-layer service.
**Why:** Cardinal layer rule (AGENTS.md): "If you see PascalCase RM field names outside `app/Modules/Integrations/RentManager/` → STOP. That logic belongs in the RM layer." RULES.md "Layer discipline" confirms this holds even with one caller. The same method already routes the primary-contact phone through `RentManagerTenantMapper::buildPrimaryContactPhonePayload()` (line ~318) — so the household relationship/phone payloads are the inconsistent exception. `PhoneNumberTypeID => 1` also duplicates the mapper's `DEFAULT_PHONE_TYPE_ID` const as a magic literal. Extra consequence: the `getTenant` embed for `updateTenant` is `PrimaryContact.PhoneNumbers,Contacts` (line ~304) — no `Contacts.PhoneNumbers` — so this inline phone write has no existing `PhoneNumberID` to echo and will DUPLICATE a household member's phone on every re-submit, unlike the primary-contact path which echoes it via `echoExisting`.
**Suggested fix:** Add `buildHouseholdRelationshipPayload()` and `buildHouseholdPhonePayload()` (the latter echoing an existing `PhoneNumberID`, mirroring `buildPrimaryContactPhonePayload`) to `RentManagerTenantMapper`; have the service just pass the returned arrays through. Add `Contacts.PhoneNumbers` to the `updateTenant` embed so the echo works.
**Comment for the dev:** The household relationship/phone writes build RRM PascalCase payloads inline in `OnboardingService` — that crosses the RM/SA layer boundary. The primary-contact phone in the same method already goes through `RentManagerTenantMapper::buildPrimaryContactPhonePayload()`; let's mirror that for household relationship + phone so all RRM field names stay in the mapper. Bonus: routing the phone through the mapper's `echoExisting` also stops duplicate phone rows on re-submit (the `updateTenant` embed would need `Contacts.PhoneNumbers` for that to work).

### SHOULD-FIX

**File:** `app/Modules/Onboarding/Controllers/TenantOnboardingController.php` (+ `app/Modules/Onboarding/routes.php`, `OnboardingService::showTenant`)
**Code snippet** (lines ~58-61):
```php
    public function show(string $tenantId): JsonResponse
    {
        return response()->json($this->onboarding->showTenant((int) $tenantId));
    }
```
**Severity:** should-fix
**What's wrong:** `GET /onboarding/tenants/{tenantId}` has no ownership check — any authenticated user can read any tenant's full PII (DOB, phone, email + every household member's DOB/phone/relationship) by guessing/iterating the id.
**Why:** IDOR. `showTenant` runs under `asSystem()` (global RM token), so RM's own location-scoping — the accidental guard the scoped user token gave the PATCH/other flows — no longer applies here. This is net-new PII exposure (household members) beyond the existing owner/vendor/tenant PATCH debt. Dev acknowledged it in the PR body as a known gap.
**Suggested fix:** Gate the route to the caller's own linked tenant: compare `{tenantId}` against `auth()->user()->linked_tenant_id` (in a FormRequest `authorize()` or a policy) and 403 on mismatch. If it's deliberately deferred to a follow-up ticket, link that ticket in the PR so it isn't lost.
**Comment for the dev:** I see you flagged the IDOR — thanks for being upfront. One thing worth weighing before merge: this GET runs under `asSystem()` and returns household members' DOB/phone too, so it's a bit more exposure than the existing PATCH debt. Simplest gate is checking `{tenantId} === auth()->user()->linked_tenant_id` and 403 otherwise. If you'd rather defer, let's file the ticket and reference it here.
