## Findings

### 🟡 Should-fix (systemic debt — originally flagged blocker, downgraded after verifying scope)

**File:** `app/Modules/Onboarding/Controllers/TenantOnboardingController.php` (+ `routes.php`, `OnboardingService.php::showTenant`)
```php
public function show(string $tenantId): JsonResponse
{
    return response()->json($this->onboarding->showTenant((int) $tenantId));
}
```
```php
public function showTenant(int $tenantId): array
{
    return $this->rentManagerService->asSystem(function () use ($tenantId) {
        $raw = $this->rentManagerService->getTenant(
            (string) $tenantId,
            ['embeds' => 'PrimaryContact.PhoneNumbers,Contacts.PhoneNumbers,Contacts.UserDefinedValues'],
        )['data'] ?? [];
```
- **What's wrong:** New `GET /onboarding/tenants/{tenantId}` has no ownership check; any authenticated user can enumerate IDs and read any tenant's full profile.
- **Why:** Runs under `asSystem()` (global token) so RRM location-scoping no longer protects it; `tenantId` comes raw from the path. Response exposes PII incl. household members' DOBs (test uses DOB `2015-06-01` → minors). The finding is an ABSENCE of a guard, not a bad line — confirmed by the route group at `routes.php:45` (`api, auth:sanctum, rm_token.valid, throttle:60,1`), which has NO `rm_super_admin` and NO ownership middleware.
- **Downgrade rationale:** `PATCH tenants/{tenantId}` (routes.php:85) and owner/vendor updates live in the SAME group with the SAME gap — this authz hole already ships on `dev`. This PR does not introduce the bug class; it adds one more (read) surface to a pre-existing systemic gap. Blocking only this PR would be inconsistent.
- **Suggested fix:** Dedicated authz ticket covering the whole Onboarding surface (me/owner/vendor/tenant, read + write): derive the entity from `Auth::user()->linked_tenant_id` like `/me` does, return 403/404 on mismatch. Not a gate on this PR alone.

### NEW 🟡 Should-fix — `createTenantLease` failure is not actually recoverable
**File:** `app/Modules/Onboarding/Services/OnboardingInviteService.php`
```php
$leaseId = $data->entity_type === 'sa_tenant'
    ? $this->createTenantLease($entityId, $data)
    : null;
```
- **What's wrong:** The docblock says a failure in the Lease step is "recoverable (tenant can still log in
  and self-onboard; only the Lease is missing)", but the call is unguarded. If `createLease` throws, `invite()`
  throws → the admin gets a 500 and never receives the response (`user_id`/`entity_id`/`lease_id`).
- **Why it bites:** the RM user + entity + SA link are already persisted at that point. Per RULES.md
  (AddUser partial-failure rule), the username is consumed, so a naive retry returns a duplicate error →
  genuinely stuck state. The documented graceful degradation is not implemented. Also violates the
  fan-out per-item isolation rule (try/catch \Throwable, sanitized log, partial success).
- **Suggested fix:** wrap the Lease step in try/catch, log sanitized (`$e::class` + message only), return
  `lease_id: null` so the invite still succeeds. No test covers the failure path today.
