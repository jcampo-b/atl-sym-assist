## Findings

### Blocker

**File:** `app/Modules/Onboarding/Services/OnboardingService.php`
**Code snippet:**
```php
                $row = $changes->household_members[$i] ?? [];
                if (($row['relationship'] ?? null) !== null) {
                    $this->rentManagerService->saveContactUserDefinedValue($contactId, [
                        'UserDefinedFieldID' => (int) config('rent_manager.tenant_relationship_udf_id'),
                        'Value' => $row['relationship'],
                    ]);
                }
                if (($row['phone'] ?? null) !== null) {
                    $this->rentManagerService->saveContactPhoneNumber($contactId, [
                        'PhoneNumber' => $row['phone'],
                        'PhoneNumberTypeID' => 1,
                        'IsPrimary' => true,
                    ]);
                }
```
**What's wrong:** RRM PascalCase payloads built directly in the SA-layer Service, not in `RentManagerTenantMapper`.
**Why:** Violates the cardinal layer rule in `.atl/AGENTS.md`. Inconsistent with this same PR's own pattern for the primary contact's phone (`buildPrimaryContactPhonePayload()`). Also duplicates the mapper's `DEFAULT_PHONE_TYPE_ID` constant via a bare `1` literal.
**Suggested fix:** Add `buildHouseholdMemberRelationshipPayload()` / `buildHouseholdMemberPhonePayload()` to the mapper, mirroring `buildPrimaryContactPhonePayload()`, and reuse `DEFAULT_PHONE_TYPE_ID`.
**Comment for the dev:** The household-member relationship/phone payloads are built inline here with raw RM field names — that's the one spot in this PR that steps outside the RM layer. Since the primary contact's phone already has a mapper builder, could you add matching ones for the household member case? Bonus: reuse `DEFAULT_PHONE_TYPE_ID` instead of the literal `1`.

**File:** `app/Modules/Onboarding/Controllers/TenantOnboardingController.php`
**Code snippet:**
```php
    public function show(string $tenantId): JsonResponse
    {
        return response()->json($this->onboarding->showTenant((int) $tenantId));
```

**What's wrong:** No check that the authenticated user owns `tenantId` — any authenticated user can read any tenant's full profile (email, DOB, phone, household members).

**Suggested fix:** Scope to `Auth::user()->linked_tenant_id === $tenantId`, or track as one cross-cutting ownership-check ticket covering owner/vendor/tenant GET+PATCH.
**Comment for the dev:** Good call flagging this in the PR notes. Since this endpoint returns more PII than the existing PATCH gap, might be worth opening the ownership-check ticket now rather than after a third endpoint lands on the same debt.
