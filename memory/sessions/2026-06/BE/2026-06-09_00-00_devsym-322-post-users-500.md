# DEVSYM-322 — POST /api/users 500 fix

## What was done
Fixed a 500 on POST /api/users caused by a post-create refetch that raced RM's
commit of the UserRoles join record. Removed the refetch entirely. The POST
response now returns `roles: []`; callers retrieve roles via GET.

## Files touched

### Modified
- app/Modules/Users/Services/UserService.php — removed getUsers() refetch after
  assignUserRole + assignUserLocation; return now uses $raw from createUser directly
- app/Modules/Integrations/RentManager/Mappers/RentManagerUserMapper.php — deleted
  refetchByIdParams() (no callers after fix)
- RESTClient/users-creation.http — added DEVSYM-322 section with SA endpoint
  create + verify requests

### Created
- tests/Unit/Modules/Users/Services/UserServiceCreateTest.php — three cases:
  getUsers never called, roles=[] when no UserRoles in raw, field mapping correctness

## Decisions made
- POST /api/users contract: `roles` is intentionally `[]` in the create response.
  Role names are available via GET. No synthetic role builder added.
- refetchByIdParams() deleted (not just inlined) — had no callers after the fix.

## Known traps discovered

### RM_DEFAULT_USER_LOCATION_ID must be set in .env
Without it, `assignUserLocation` receives `0` and RM returns 500. The service
throws a RuntimeException early (`config('rent_manager.default_user_location_id') <= 0`),
but only if the key is present and evaluates to 0. If the key is missing entirely,
`(int) null` is also 0, same result.

### POST /api/users requires RM admin credentials for manual verification
User 4MK (UserID 393) does not have Manage Users permissions in any RM location
in the dev environment. Manual verification of the POST requires Jeremy (UserID 3)
or Doug (UserID 42) credentials. The token flow in RESTClient/users-creation.http
uses `{{$dotenv RENT_MANAGER_USERNAME}}` — swap to an admin account for DEVSYM-322
verification.

### RM persists the user even when assignRole/assignLocation fails
`createUser` succeeds and commits the row before `assignUserRole` or
`assignUserLocation` is called. A failed subsequent call leaves an incomplete
user in RM with the username consumed. Re-running the create request with the
same username will return a duplicate error from RM.

### Root cause of the 500 was the refetch, not the assign calls
The race condition was on `getUsers()` immediately after `assignUserRole` — RM
hadn't finished committing the UserRoles join record yet. The `assignRole` and
`assignLocation` failures seen in dev are a separate permissions issue (see above),
not related to the original bug.
